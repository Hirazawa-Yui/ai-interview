# 04-RAG 检索评测

> 性质：参考文档（评测基线 + 复现步骤）· 更新日期：2026-09-27 · 对应任务：T29
> 语料：`kb_id=15`《Redis设计与实现》（黄健宏）816 块 / 318,082 字 · 标注集 **70 题** · 单文档、单次评测

## 1. 结论速览

| 结论 | 数据支撑 |
|---|---|
| **检索环节整体健康，不是瓶颈** | 全量 Hit@5 = **85.7%**、片段召回 Rec@5 = **86.9%**；「规范」形态下达 97.5% / 96.3% |
| **Query Rewrite 有效，但只在特定形态上** | 「词汇不匹配」Hit@5 **73.3% → 80.0%**、「短查询」**66.7% → 80.0%**（+6.7pp / +13.3pp）；**「规范」问句上 0 收益**（97.5% → 97.5%） |
| **动态 Top-K 零收益、纯成本（硬证伪）** | 四组指标**逐位相同**——即使 D 组有 9 题真实走 topK=12、7 题走 topK=20；上下文却 **+21.5%**（3878 → 4712 字符） |
| **minScore 0.10–0.40 空转，但**不该往上调 | 0.10–0.40 指标完全一致（阈值低于分数下限）；0.50 起开始损伤命中率，0.60 要付 8.6pp 的 Hit@5 |

> ⚠️ 简历里「配合动态 Top-K 策略提升检索召回率」**被数据证伪**；而「Query Rewrite 提升检索」**在该起作用的场景下成立**。改写建议见 §5。

## 2. 评测设计

**语料**：kb_id=15《Redis设计与实现》，318,082 字 → 816 块（`chunk.size=500 / overlap=80`）。

### 2.1 标注集：两个正交维度（70 题 / 84 个 gold 片段）

**维度一「形态」——决定这道题用来检验哪个机制**（本次评测最关键的切分）：

| 形态 | 题数 | 设计意图 | 例 |
|---|---|---|---|
| 规范 | 40 | 对照组：术语准确、意图完整的问句 | 「SDS 保存的空字符会计入 len 属性吗？」 |
| **词汇不匹配** | 15 | 检验 **Query Rewrite 的词汇桥接**：意图单一、答案唯一，但用词刻意偏离文档术语 | 「Redis 存字符串会不会像 C 那样越界？」（文档术语是「杜绝缓冲区溢出」） |
| **短查询** | 15 | 检验 **动态 Top-K 的短查询档**：≤4 字触发 topK=20、5–15 字触发 topK=12，且 gold 必须够窄 | 「跨度」「惰性删除」「ziplistPush」 |

**维度二「类型」**——考察点：事实型 31 / 概念型 23 / 对比型 8 / 多跳型 8。

### 2.2 关键设计决策

- **gold 标「答案所在的关键句片段」而非 chunk 编号**——编号随分块参数失效，句子不会。判定 = top-K 结果的 `content` 是否包含该片段（比对前**两侧都去空白**，因为 PDF 正文在句子中间夹着排版硬换行）。共 84 个片段。
- **两套指标口径**（因为不少题的答案横跨 2–3 个片段）：`Hit@K` 题目级（**至少**命中一个，宽松）/ `Rec@K` 片段级（多跳题需全中，严格）/ `MRR@5`。
- **四组消融（2×2）**，minScore 统一固定 0.28 以隔离变量：A 原问题+topK8（基线）/ B 改写后+topK8 / C 改写后+动态topK（**现状**）/ D 原问题+动态topK（**设计意图**）。
- **改写结果冻结写回标注集**，后续运行复用同一份——否则 B/C 两组各调一次 LLM，用的不是同一改写文本，对比无意义。重跑时 LLM 调用为 0。
- **脚本自检**（每次运行先跑）：① 用生产同一个 `OverlapTextSplitter` 离线重建 chunk 序列并与库中 `chunkCount` 比对（实测 816=816 精确相等）；② 逐个校验 gold 片段能否命中至少 1 个 chunk；③ 提示「区分度偏低」（命中 >3 块）与「与他题撞块」的片段。

> **为什么必须分「形态」**：最初的 40 题全是规范问句，长度 ≥16 字的占 39 题、≤4 字的 **0 题**——**动态 topK 的短查询档一次都没被触发过**，rewrite 的词汇桥接也无从发挥。在那种分布上得出「两者都无收益」是把特征当结论，属于标注集设计缺陷。

## 3. 结果

### 3.1 四组消融对照（N=70，minScore 固定 0.28）

| 组 | 说明 | Hit@1 | Hit@3 | Hit@5 | Rec@5 | MRR@5 | 平均块数 | 平均上下文字符 |
|---|---|---|---|---|---|---|---|---|
| A | 原问题 + topK8（基线） | 55.7% | 80.0% | 85.7% | 86.9% | 0.679 | 8.0 | 3878 |
| B | 改写后 + topK8（rewrite 净效果） | 55.7% | 82.9% | 90.0% | 90.5% | 0.695 | 8.0 | 3876 |
| C | 改写后 + 动态topK（**现状**） | 55.7% | 82.9% | 90.0% | 90.5% | 0.695 | 9.4 | **4570** |
| D | 原问题 + 动态topK（设计意图） | 55.7% | 80.0% | 85.7% | 86.9% | 0.679 | 9.7 | **4712** |

**A 与 D 逐位相同、B 与 C 逐位相同**：动态 topK 对指标的贡献恰好为 0，代价是把上下文撑大 **+21.5%**（A→D）。

### 3.2 按问题形态分层：Hit@1 | Hit@5 | Rec@5 ← **本次核心表**

| 形态 | 题数 | A（基线） | B（+rewrite） | C（现状） | D（设计意图） |
|---|---|---|---|---|---|
| 规范 | 40 | 72.5% / 97.5% / 96.3% | 70.0% / 97.5% / 96.3% | 70.0% / 97.5% / 96.3% | 72.5% / 97.5% / 96.3% |
| **词汇不匹配** | 15 | 40.0% / **73.3%** / 73.3% | 46.7% / **80.0%** / 80.0% | 46.7% / 80.0% / 80.0% | 40.0% / 73.3% / 73.3% |
| **短查询** | 15 | 26.7% / **66.7%** / 66.7% | 26.7% / **80.0%** / 80.0% | 26.7% / 80.0% / 80.0% | 26.7% / 66.7% / 66.7% |

三条读法：

1. **rewrite 的收益正好落在它该起作用的形态上**：词汇不匹配 +6.7pp、短查询 +13.3pp，规范形态 **0**。机制得到验证，也解释了 §2.2 那个设计缺陷为何会导出错误结论。
2. **动态 topK 在所有形态上都无收益**：A vs D、B vs C 在每个形态内都逐位相同——包括短查询形态（14 题里有 9 题在 D 组走 topK=12、7 题走 topK=20）。
3. 新增两簇确实更难（规范形态 Hit@5 97.5%，短查询只有 66.7%），说明它们有区分度，不是凑数。

（C 组只有 3 题走到 topK=20，因为改写会把短查询变长、落回低档——这正是 `KbQueryServiceImpl:80` 按**改写后**长度选档的表现。）

### 3.6 可复现性：哪些数字能逐位复现、哪些不能

两次完整运行的 MRR 曾对不上，据此做了针对性诊断，**根因在上游**：

- **`qwen3.7-text-embedding` 对同一输入不是确定性返回**：同进程内连调三次、输入完全相同的文本，向量元素级差异约 **1.5e-4**（偶发而非必然）。
- 相似度分数随之抖动同量级，当两个文档分数差小于抖动幅度时，**相邻名次会互换**。

实测影响范围：

| 观测项 | 跨运行稳定性 |
|---|---|
| 命中**集合**（哪些块进 top-8） | ✅ **40/40 题完全不变** |
| 文档**顺序** | ⚠️ 40 题中 1 题发生过相邻名次互换 |
| `Hit@5` / `Rec@5` / 块数 / 上下文字符 | ✅ 两次运行完全一致 |
| `Hit@1` / `MRR@5` | ⚠️ 存在 **±0.005 量级**抖动（名次敏感） |

**引用建议**：`Hit@5`、`Rec@5`、上下文体积可逐位引用；`MRR@5` 保留两位小数（**≈0.68**）。

## 4. 结论解读

1. **Query Rewrite 该保留，但要知道它在为谁工作**。它在词汇不匹配（+6.7pp）和短查询（+13.3pp）上有明确收益，在规范问句上收益为零。成本是每次问答多一次 LLM 往返（T17 实测 0.46–0.67s）。**收益为正但不是免费的**——如果将来要省这一次调用，依据应该是「用户输入偏规范」这一产品判断，而不是「rewrite 没用」。

2. **动态 Top-K 建议下线或改为固定 topK**。这是本次最硬的结论：在三档档位**全部被触发**的情况下（D 组 9 题 topK=12 + 7 题 topK=20），五个指标与固定 topK=8 逐位相同，而上下文多出 21.5%。「短查询关键词少所以要更多候选」这个设计假设，在这套语料上没有被数据支持。附带一提，现状实现还额外按**改写后**长度选档（`KbQueryServiceImpl:80`），把短查询推向更低的档位——但既然动态档位本身无收益，修这个 bug 也没有意义。

3. **minScore 保持现状（或按语料标定），不要凭直觉调高**。0.10–0.40 空转意味着当前配置是「保守但无害」；往上调会开始损失命中率。要调必须用本评测脚本在目标语料上重新扫一遍——**不同语料的分数下限差别很大**。

4. **检索不是这套 RAG 的瓶颈**。规范问答下 Hit@5 97.5%，说明正确段落几乎总能进入喂给 LLM 的上下文。结合 T18/T19 的耗时结论（`生成` 段约 1.7–1.85 ms/输出字节），继续优化应当从**生成侧**入手。

## 5. 对简历表述的影响

原表述：

> 知识库问答：基于 RAG 实现知识库文档内容精准检索生成，支持多轮问答；引入 LLM 驱动的 Query Rewrite 改写用户意图，配合动态 Top-K 策略提升检索召回率。

两个问题：①「动态 Top-K 提升检索召回率」**被数据证伪**；②「Query Rewrite 提升检索」**只在特定场景成立**，笼统地说会被追问细节。建议改为分层结论——**能说清「什么情况下有用、什么情况下没用」比笼统说「有用」更能体现工程判断力**：

> 自建 70 题人工标注检索评测集（按问题形态分「规范/词汇不匹配/短查询」三簇，按考察点分事实/概念/对比/多跳四类），离线消融实验量化各模块收益：Query Rewrite 在表述规范的问句上收益为 0（Hit@5 97.5%），但在术语不匹配与短查询上分别提升 Hit@5 6.7pp 和 13.3pp；**动态 Top-K 则在三档档位全部触发的情况下指标零提升、上下文 +21.5%，据此判定可下线**。同时标定出 minScore 阈值在 0.10–0.40 区间完全空转、0.50 起开始损失召回。

## 6. 局限（引用数据时必须带上）

- **单文档、70 题**：统计效力有限（一个 ±1 题就是 6.7pp，短查询簇尤甚），**不外推**到其他语料或领域。
- **「与他题撞块」**：自检报出 18 个 gold 片段与另一道题指向同一个 chunk（30 道新题中 16 道涉及）。这不影响指标正确性（每题独立判定），但会降低**样本独立性**的上限。注意撞块不等于结果冗余——实测题 35（规范）命中 chunk 72 而题 47（词汇不匹配）在同一个 chunk 上 miss，因为 query 不同结果就不同。
- **短查询簇的答案歧义**：≤4 字查询（如「跨度」）本身答案偏宽，已刻意挑选**指向单一具体事实**的短词来压缩歧义，但主观性仍高于其他簇。
- **gold 由 Claude 出题、用户逐条复核**：不是独立第三方标注，存在标注者偏差。
- **只测检索，不测生成**：本评测回答「正确段落有没有被检索到」，**不回答「LLM 答得对不对」**。
- **上游 embedding 非确定性**：`qwen3.7-text-embedding` 服务本身的特性，非本项目 bug；意味着任何基于相似度名次的判断都有 ~1.5e-4 的固有噪声（见 §3.6）。
- 评测期间后端必须**没有在途的向量化任务**，否则评测进程的消费者线程会与主后端抢同一条 Redis Stream 消息。

## 7. 复现步骤

**前置**：PG(5432) / Redis(6380) / `DASHSCOPE_API_KEY` 就绪；目标知识库 `vector_status=COMPLETED`。

**方式一（推荐）**：IDEA 里打开 `backend/`，Run Configuration 的 EnvFile 指向 `backend/.env`，直接右键运行
`backend/src/test/java/com/aiinterview/rag/RagRetrievalEval.java` 的 `main`。报告打印到控制台并写入 `target/rag-eval/result.txt`。

**方式二（命令行）**：classpath 过长必须走 Java argfile，见 `docs/03-任务清单.md` T29 记录里的命令序列。

**脚本自身的安全网**（每次运行都会先跑）：

1. 用生产同一个 `OverlapTextSplitter` **离线重建 chunk 序列**，与库中 `chunkCount` 比对——实测两次都精确相等（816=816、839=839），证明离线复现与生产入库等价；
2. 逐个校验 gold 片段能否命中至少 1 个 chunk（0 个 = 抄错或跨块，会点名报出）；
3. 提示命中超过 3 块的「区分度偏低」片段、以及与他题撞块的片段。

**成本**：一次完整运行 = 70 次 LLM 改写（仅首次，之后为 0）+ 约 1100 次 embedding 调用。

**换语料/改参数后**：删除 `rag-gold.json` 里所有 `rewritten` 字段重跑（会重新调 LLM 改写）；若改了 `chunk.size/overlap`，旧标注集整体失效，需重新标注——自检里的「重建块数 vs chunkCount」会对不上并报警。
