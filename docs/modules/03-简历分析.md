# 03-简历分析

> 模块文档 · 对应代码基线：master · 更新日期：2026-09-07

## 1. 功能概述
简历上传（PDF/DOC/DOCX/TXT，单次 multipart）→ Tika 解析文本 → OSS 存储 → **Redis Stream 异步 LLM 分析**（评分 + 优势 + 建议）→ 前端轮询状态展示。支持 MD5 去重秒返、重新分析、分析历史（一对多）。简历是小文件（<10MB），不走分片上传，只复用 `file/service/IFileStorageService.java` 的 OSS 读写。

## 2. 涉及文件
后端：
- `resume/controller/ResumeController.java` — 5 端点：upload / list / {id}/detail / delete / {id}/reanalyze
- `resume/service/impl/ResumeServiceImpl.java` — 上传编排（类型校验→Tika→MD5去重→OSS→入库 PENDING→XADD）
- `resume/service/impl/ResumeParseServiceImpl.java` — Tika 封装（AutoDetectParser，5MB 文本上限，去控制字符/合并空行）
- `resume/service/impl/ResumeAnalysisServiceImpl.java` — LLM 分析（BeanOutputConverter 结构化输出 + 三层防护）
- `resume/listener/ResumeAnalysisProducer.java` / `ResumeAnalysisConsumer.java` — Stream 任务（模板：`stream/AbstractStreamProducer/Consumer`）
- `resume/entity/Resume.java`（状态机 PENDING/PROCESSING/COMPLETED/FAILED）、`resume/entity/ResumeAnalysis.java`（一对多分析历史）
- `resume/dto/ResumeAnalysisResponse.java` — LLM 结构化输出 DTO（overallScore/summary/strengths[]/suggestions[]）
- `resources/prompts/resume-analysis-system.st` / `resume-analysis-user.st`

前端：`pages/UploadPage.vue`（上传+列表+状态轮询+详情弹窗+删除+重分析）、`api/resume.js`

## 3. 核心流程
```
POST /api/resumes/upload (multipart)
  → Tika 校验类型 + 解析文本 → MD5 去重（同 md5 且 COMPLETED → 秒返 duplicate:true）
  → OSS putObject（resumes/{date}/{uuid8}_{原名}）→ 入库 status=PENDING
  → XADD resume:analyze:stream {resumeId, content}
  → 返回 {resumeId, analyzeStatus:"PENDING"} → 前端列表轮询状态

消费者（单线程守护，XREADGROUP analyze-group）
  → markProcessing → LLM 分析（system 模板 + JSON Schema + 防注入指令；user 模板替换 {resumeText}）
  → guardOutput → BeanOutputConverter 解析
  → 入库 resume_analyses（strengths/suggestions 序列化为 JSON 字符串）
  → markCompleted；失败 retry<3 重 XADD，≥3 markFailed，均 ACK
```

## 4. 实现细节
- **异步的原因**：LLM 分析 5~15s，同步会挂 HTTP 请求。状态机驱动前端轮询（与面试评估模式一致）。
- **去重**：仅"同 md5 且已完成分析"秒返；同 md5 但 FAILED 的会重新上传入库（覆盖旧记录行为：插新行）。
- **删除**：OSS 文件（失败仅告警）+ 分析记录 + 简历行，`@Transactional`。
- **重分析**：置 PENDING 清 error → 重新 XADD（复用已有 parsedText，不重解析）。
- **分析后二次查库**：AI 调用耗时期间简历可能被删，保存结果前再查一次存在性。
- 明细 JSON 结构：`strengthsJson` 是 `["...","..."]`，`suggestionsJson` 是 `[{"category","issue","suggestion"}]` —— **前端 UploadPage 按此结构渲染**。

## 5. 数据
- 表：`resumes`、`resume_analyses`（见 docs/01-数据模型.md）
- Stream：`resume:analyze:stream` / group `analyze-group` / consumer 前缀 `analyze-consumer-`

## 6. 已知坑位
- 类型校验靠 Tika 检测（`detectContentType`），绕过伪装文件名的概率低但存在；解析出的文本无敏感信息过滤。
- 上传时 Tika 解析与 OSS 上传同步执行，大简历（接近 10MB）请求耗时长（前端已设 120s 超时）。
- ~~`ai_raw_response` 恒存空串~~：✅ 已修（B5，2026-09-08）——现存 `ResumeAnalysisResponse` 序列化 JSON（与面试评估侧对称，调试抓手恢复）。
- **⚠️ 上传事务内 XADD 可见性竞态**：`upload()` 带 `@Transactional`，XADD 发生在事务提交前，消费者线程可能先于提交读到行 → `processBusiness` 中 `selectById` 为 null 提前 return，消息被静默 ACK 丢弃（跨模块坑 #8；T3 验证时疑似命中 1 次——10ms 内"任务处理完成"但无分析记录、无重试日志，重触发后正常）。修复思路待设计：XADD 移出事务（事务同步 afterCommit）或消费者对 null 行不 ACK 改重试。

## 7. 验证要点
1. Swagger `POST /api/resumes/upload` 传 PDF → 返回 PENDING → 观察后端日志 "简历分析 任务处理完成"
2. `GET /api/resumes` 列表 latestScore 出现 → `GET /api/resumes/{id}/detail` 查看 analyses 数组
3. 重复上传同文件 → duplicate:true 秒返
4. `POST /{id}/reanalyze` → 列表回到 PROCESSING → 完成后 analyses 多一条历史
5. 前端 UploadPage：上传 → 自动刷新到 COMPLETED → 详情弹窗评分仪表盘/优势/建议渲染正常
