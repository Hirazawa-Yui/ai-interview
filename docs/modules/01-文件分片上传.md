# 01-文件分片上传

> 模块文档 · 对应代码基线：master · 更新日期：2026-09-07

## 1. 功能概述
大文件（知识库文档，≤200MB）高可靠上传：前端 5MB 切片并发上传 → OSS 服务端合并。支持 **MD5 秒传**（同文件免传）、**断点续传**（刷新/暂停后跳过已传分片）、**暂停**（AbortController）。简历上传不走此模块（小文件直接 multipart）。

## 2. 涉及文件

前端（`frontend/src/`）：

## 3. 核心流程
```
选文件 → 前端算全文件 MD5
  → POST /api/file/check {md5, fileName, fileSize, totalChunks}
       ├─ DB file_info 有该 md5 → {completed:true, url} 秒传
       ├─ Redis file:upload:{md5} 存在 → {uploadId, uploadedChunks} 断点续传
       └─ 否则 → OSS CreateMultipartUpload + Redis 建会话 → {uploadId, []}
  → 并发上传分片 POST /api/file/chunk（并发 ≤3）
       每个分片：前端传 chunkMd5 → 后端先 MD5 校验（先验后传）→ OSS UploadPart(partNumber=index+1)
       → 记账 SADD file:chunks:{md5} + HSET file:etags:{md5}（OSS 确认后才记账）
  → 全部分片完成 → POST /api/file/merge
       Redisson 锁(file:merge:{md5}) → DB 幂等校验 → SCARD==totalChunks
       → OSS CompleteMultipartUpload(partETags 按 partNumber 排序)
       → 大小比对校验 → 入库 file_info → 清理 Redis 三键 → 返回 url
  → 前端拿 url，取 pathname 作 fileKey 交给知识库入库
```

## 4. 实现细节
- **fileKey 生成**：`files/{yyyy/MM/dd}/{md5前8位}{扩展名}` —— 用 md5 前缀做文件名主体，避免中文文件名导致 OSS 签名错误（`initiateMultipartUpload` 也不设 contentDisposition，同理）。
- **TTL**：三键均 24h，每次分片成功后续期。
- **合并锁**：实际用 Redisson `tryLock(3s 等待, 120s 持有)` 看门狗续期（非 PLAN 里写的 SETNX 60s）；抢不到锁先查 DB，已有结果直接返回（合并幂等）。
- **完整性**：合并后 `HeadObject` 比对文件大小（OSS Complete 后拿不到整文件 MD5，用大小近似校验）。
- **先落 OSS 后记账**：保证 Redis 里记录的都是 OSS 已确认的分片。
- **前端暂停**：AbortController 批量 abort；`uploadedChunks` 数组即时更新，恢复上传（重新选文件 → check 返回已传列表）自动跳过。注意 abort 只阻止**新的**分片发射，在途分片仍会跑完并计数。
- **前端进度显示（T24）**：只展示**百分比**（进度条 + 「已完成 N%」文案），不再显示「已上传 X / Y 个分片」这类分片计数，文件信息区也去掉了「分片数」一栏。百分比仍按分片数算：`uploadPercent = round(已传分片数 / 总分片数 * 100)`。

## 5. 数据
- 表：`file_info`（见 docs/01-数据模型.md）
  - **生命周期**：唯一写入口是 `merge()` 的 insert；唯一删除口是 `deleteByStorageKey()`（T25，删知识库时按 `storage_key` 清理）。不变式：**file_info 有行 ⇔ 该 OSS 对象存在**——破坏它就会出现"秒传命中一个已删除的 URL"的死链。
- Redis（db 1，TTL 24h）：`file:chunks:{md5}` Set、`file:upload:{md5}` Hash{uploadId,totalChunks,fileName,fileSize,fileKey}、`file:etags:{md5}` Hash{partNumber→eTag}、`file:merge:{md5}` 锁

## 6. 已知坑位
- ~~孤儿 MultipartUpload 无清理~~：✅ 已修（D1，2026-09-08）——`FileChunkServiceImpl.cleanupExpiredMultipartUploads` 定时任务（启动 15s 后 + 每 24h）扫描 OSS `files/` 前缀未完成上传，超过 24h 的 abort（存储层新增 `listMultipartUploads`/`abortMultipartUpload`）；`Application` 已开 `@EnableScheduling`。首次运行实测清掉 4 个历史孤儿。
- ~~**删除知识库后 `file_info` 残留秒传登记**~~：✅ 已修（T25，2026-09-22）——删知识库只删了 OSS 对象和 knowledge_bases 行，`file_info` 里的登记留着 → 同一文件再上传时 `check()` 秒传命中一个**已删除的 URL**，随后 `/api/knowledge/upload` 下载该对象失败。修法：`IFileChunkService.deleteByStorageKey(storageKey)`（按 `storage_key` 精确删，不用 md5 兜底以免误删存活 key 的登记），在 `KnowledgeBaseServiceImpl.delete()` 的同一事务内调用、**异常直接抛出**（吞掉会让事务提交掉这行必须清掉的脏数据）。
  - **实测（2026-09-22）**：上传测试文件 → `file_info` 有行 → 删知识库 → 该 `storage_key` 行数**归 0**（日志 `清理秒传登记: storageKey=…, rows=1`）→ 重传同一文件 `check` 返回 `completed:false`（不再秒传命中死链，走完整上传）。
  - 历史遗留：修复前产生的孤儿登记不会自动回补，需要时手工按 storage_key 清（本次已清掉 kb1/kb2/kb5 对应的 3 行）。**注意**：只上传未入库的文件（用户传了但没点"确认入库"）本就没有 knowledge_bases 行，属于正常状态，不要当成孤儿误删。
- `uploadChunk` 无分片大小上限校验，仅靠全局 multipart max 100MB。
- 前端上传中切换路由会 abort，但 Redis 会话保留 —— 重新选同一文件走断点续传，符合预期。
- **前端暂停后无法恢复**：`pauseUpload` 后按钮 `v-if="uploading"` 消失，UI 上没有「继续上传」入口（`startUpload` 只由选文件触发）。属已知小瑕疵，未修。

## 7. 验证要点
1. Swagger 或前端：上传一个 >10MB PDF，观察 check→chunk→merge 三阶段日志
2. 秒传：同一文件再传一次，check 直接返回 completed=true
3. 断点续传：上传中暂停（前端按钮），刷新页面重选同文件，跳过已传分片
4. 完整性：merge 返回 url 后 `GET /api/file/preview/{md5}` 应报"未找到上传记录"（Redis 已清理）；DB file_info 有记录
4.1 进度显示（T24）：上传时界面只见百分比进度条与「已完成 N%」，没有分片计数文案
4.2 秒传登记随库清理（T25）：上传文件 → 记下 `SELECT storage_key FROM file_info WHERE file_name='…'` → 删对应知识库 → 该行应消失；再传同一文件 `check` 返回 `completed:false`（走完整上传）
5. 幂等：对同 md5 并发调两次 merge，第二次应直接返回已有 url
